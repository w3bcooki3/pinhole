See what the internet can reach in your AWS network.

Pinhole reads how your VPCs are configured, works out every path from the internet to your servers and load balancers, follows what an attacker could reach next, and gives you the fewest rule changes that close it. Every answer is exact, explained hop by hop, and checked by running the analysis again.

Open the console Quick start Source on GitHub

Free and open source (MIT). Runs in your browser or on the command line. Nothing is uploaded, and nothing in AWS is changed.

Three questions, answered exactly

What can the internet reach?

Every network interface and load balancer listener that accepts connections from the internet, with the exact ports, the exact source addresses that work, and the rule behind each hop.

What can an attacker reach next?

If one of those servers is compromised, the databases, caches, control planes and admin ports it can open, inside your VPCs and across peered accounts.

What is the smallest fix?

The fewest changes that close every critical and high risk. Each one is applied to a copy of your network and re-analysed, so it is proved, with the AWS CLI command to run.

Why it exists

Whether a server is reachable from the internet depends on five things at once: a public address, an internet gateway, the subnet's routes, the network ACL in both directions, and every security group on the interface. A load balancer adds its own groups, ACLs and targets. The AWS console shows each of these on its own page; none of them answers "is this open, and why?"

Getting it wrong goes both ways. A rule that looks open can be harmless because the response has no route back. A rule that looks narrow can be wide open because another group on the same interface allows everything. Pinhole puts all of it together and gives one answer, with the evidence.

Who it is for

  • Cloud and platform engineers who want to know what a change really opens before and after they make it.
  • Security teams who need a complete, defensible list of internet exposure and attack paths, not a sample.
  • Auditors and managers who need a clear report they can read without opening the AWS console.

What it is not

Pinhole analyses configuration, not traffic. It does not scan your servers, read logs, or know what software listens on a port. It covers VPC network paths to interfaces and Application and Network Load Balancers; services that are public by design outside a VPC, such as S3 buckets or API Gateway, are out of scope. See Limitations.

How it works

Three steps. Only the first one touches AWS, and it only reads.

  1. Collect

    A short script in AWS CloudShell, or pinhole collect, calls read-only Describe APIs and saves one JSON file per account and Region: the snapshot.

  2. Analyse

    Open the snapshot in the console or the CLI. The analysis runs on your machine, offline. It cuts the address and port space at every rule boundary, so every client and every port is covered, not sampled.

  3. Act

    Read the exposures, attack chains and the fix plan. Try changes in the simulator. Copy the AWS CLI commands you agree with and run them yourself.

Exact, not sampled

For each interface, Pinhole collects every boundary that any relevant rule draws: CIDR edges, port range edges, ACL rule edges. Between two boundaries every packet is treated the same way by every rule, so evaluating one packet per piece gives the answer for all of them. That is how a report can say "tcp/22 from 0.0.0.0/0 except 10.0.0.0/8" and be right about every address.

Reachable, blocked or unknown

Reachable
Every step allows the request and the response.
Blocked
A named step stops it, with the rule or the missing route.
Unknown
The snapshot lacks what the answer depends on, for example a route table in another account or a route to an instance acting as an appliance. Pinhole never guesses.

Quick start

Five minutes in the browser, with nothing to install. The command line is below.

In the browser

  1. Open the console. It starts on a demo environment, clearly labelled, so you can look around first.
  2. Choose Connect an account. It shows one command to paste into AWS CloudShell, which writes pinhole-snapshot-<account>-<region>.json.
  3. Download the file from CloudShell (Actions, then Download file) and drop it on the console.

The console is one HTML file. It makes no network requests, and its Content Security Policy makes the browser enforce that, so your snapshot never leaves the tab. You can also download pinhole-<version>.html from a release and open it from disk.

On the command line

Requires Node.js 22 or later.

git clone https://github.com/w3bcooki3/pinhole.git
cd pinhole
npm ci && npm run build
alias pinhole="node $PWD/packages/cli/dist/main.js"

pinhole collect --profile audit --region eu-west-1
pinhole exposure pinhole-snapshot-*.json

Collect a snapshot

A snapshot is a JSON file with the network configuration of one account in one Region. Collection uses read-only calls and takes seconds.

In AWS CloudShell

No install and no credentials on your machine. Open CloudShell in the account to check, upload cloudshell-collect.sh (the console's Connect page gives a copy-ready command that writes it for you) and run:

bash cloudshell-collect.sh eu-west-1

# several Regions
for r in us-east-1 eu-west-1 ap-southeast-2; do bash cloudshell-collect.sh "$r"; done

Download each file with Actions, then Download file, using the path the script prints.

From your machine

pinhole collect --profile audit --region eu-west-1
# writes pinhole-snapshot-<account>-eu-west-1.json, readable only by you

pinhole collect --profile audit --region us-east-1,eu-west-1 --out-dir snapshots
# one file per Region; a Region that fails does not stop the others

Permissions

The collector needs only the read-only actions in this policy. A test checks that the policy and the collector's API calls match exactly, and the collector refuses at runtime to send any call whose name does not start with Describe, Get or Search. If a call is denied, collection continues and the report says which results may be incomplete.

What a snapshot contains

VPCs, subnets, route tables, internet, NAT and egress-only gateways, virtual private gateways and VPN connections (state, routes and tunnel status only; never the tunnel keys), peering connections, transit gateways and their route tables, network ACLs, security groups and rules, prefix lists, network interfaces, instance names, VPC endpoints and the PrivateLink endpoint services you provide (with who may connect, and who has), and load balancers with their listeners, rules, target groups and target health. Rule hygiene

Besides rules that do nothing on their own, it finds rules that several others cover together, rules another attached group already covers everywhere, network ACL entries that earlier entries decide in full, the smallest equivalent rule set for each group, and groups and ACLs near their rule quotas. In CI and pull requests

Catch new internet exposure before it ships: check a Terraform plan, compare snapshots, or publish findings to GitHub code scanning.

Check a Terraform plan

Pinhole places each security group, rule, network ACL, route, attachment, Elastic IP, subnet association, internet gateway and listener change from the plan onto the snapshot, IPv4 and IPv6, including groups and gateways the plan creates, and runs the full analysis. Anything it cannot place exactly is listed as not analysed, never guessed.

terraform plan -out tfplan && terraform show -json tfplan > plan.json
pinhole plan snapshot.json plan.json --fail-on high --policy policy.json

With --policy, the check also lists every policy rule the plan would start to break, and every violation it would resolve; --fail-on then fails on broken rules at that severity too.

Policies

Write down what must never be reachable and what must always be. Pinhole checks every rule exactly, and shows the connection that breaks it.

{
  "groups": {
    "databases": { "tags": { "role": "db" } },
    "bastions":  { "securityGroups": ["sg-0bastion"] },
    "dev":       { "tags": { "env": "dev" } },
    "prod":      { "tags": { "env": "prod" } }
  },
  "rules": [
    { "id": "no-public-db", "severity": "critical",
      "deny": { "from": "internet", "to": "databases", "indirect": true } },
    { "id": "dev-not-prod", "deny": { "from": "dev", "to": "prod" } },
    { "id": "ssh-via-bastion",
      "deny": { "from": "internet", "to": { "not": "bastions" }, "ports": "tcp/22" } },
    { "id": "site-up",
      "require": { "from": "internet", "to": { "names": ["web-*"] }, "ports": "tcp/443" } }
  ]
}

Rules

  • deny fails for every connection that gets through, with the rules that let it in. From "internet", it covers direct exposure and anything behind a load balancer (on the port that reaches the target). With "indirect": true it also covers attack chains: an internet-facing server taken over that then reaches the target. Between groups, it checks every pair.
  • require fails for every pair that cannot connect, with the hop that blocks it. From "internet", the whole port range must be open to some internet address.
  • ports: tcp/22, udp/53, tcp/1024-65535, icmp or all, alone or in a list. Optional for deny, required for require.
  • severity: critical, high, medium, low or info. Deny rules default to high, require rules to medium.

Choosing resources

from and to take "internet" (as a source), "*", the name of a group, or a selector. Every key in a selector must match: tags (read from the instance, then the subnet, then the VPC; a list matches any value; * is a wildcard), securityGroups, subnets, vpcs, ids (interface, instance or load balancer IDs, ARNs or names), names (instance or load balancer names, with *), any (a list of alternatives) and not.

Where policies run

  • pinhole policy snapshot.json policy.json checks a snapshot.
  • pinhole plan snapshot.json plan.json --policy policy.json shows what a Terraform plan would break or fix.
  • pinhole fix snapshot.json --plan --policy policy.json plans fixes that keep every required connection working.
  • The console's Policies page checks every loaded snapshot as you edit. The policy stays in your browser.

The file is validated field by field; an error names the field, such as rules[2].deny.to.

Internet exposure

An interface is exposed on a port when a client on the internet can open a connection to it and get the answer back.

Over IPv4, that needs all of these:

  1. A public IP or Elastic IP on the interface.
  2. An internet gateway attached to the VPC.
  3. The network ACL allowing the request in.
  4. A security group on the interface allowing it.
  5. The subnet's route for the client's address pointing at that internet gateway.
  6. The network ACL allowing the response out, on the client's ephemeral port.

Over IPv6 no public IP is needed: any interface with an IPv6 address in a subnet routed to an internet gateway is checked, and so is every listener of a dual-stack load balancer. Load balancers are checked from the internet to the listener, then from each load balancer node to each target.

Return traffic

Security groups are stateful: if the request is allowed, so is the response. Network ACLs are not. The response leaves on the client's ephemeral port, and that range depends on the client: Linux uses 32768 to 61000, Windows 49152 to 65535, and Elastic Load Balancing 1024 to 65535. An ACL that only allows one of these ranges out works for some clients and not others. Pinhole reports that as partial, per client.

Severity

Exposures are ranked by what is on the port, whoever it is open to. Remote administration (SSH, RDP, WinRM and similar), databases and caches, and container and cluster control planes are critical. Admin panels, file sharing, directory services and message brokers are high, and so is any range of many ports. A port Pinhole does not recognise is medium. Plain web traffic on 80 and 443 is low, because it is usually meant to be public. The list is in packages/engine/src/risk.ts; it does not know what actually runs on a port.

Attack chains

If an internet-facing server is compromised, what can the attacker open from there?

Each server the internet can reach is treated as a starting point. From it, Pinhole works out every service it can open on every other interface, with the same exact analysis. The attacker moves on only through services that normally give command execution: remote administration, container and cluster control planes, and wide port ranges. A database reached on 5432 is a target, not a new foothold.

A chain is reported when it ends at a data store, a control plane or remote administration that the internet cannot reach directly. Chains to the same target are merged, with every route listed. Severity comes from what is reached, lowered when the starting point is only open on web ports, or when the chain is three hops or longer.

This is a model of what the network allows, not of what is exploitable: it assumes credentials or a vulnerability at each step.

Crown jewels and the smallest cut

Tag what matters most with pinhole:crown-jewel=true, or with a data classification of confidential, restricted, secret, sensitive or PII, on the instance, its subnet or its VPC. Chains to those rank first. Without tags, the data stores and control planes that chains end at are used.

Pinhole then finds the smallest set of security group rules whose removal leaves no attack path to any of them: a minimum cut on the attack graph, computed with max flow. Each edge costs the rules that must all go to cut it, and the costs are weighted so that closing a public website, or a rule that names a security group, is a last resort. The result is pruned until every rule in it is needed, then checked by removing the rules from a copy of the snapshot and running everything again.

Across accounts and Regions

Load snapshots from both sides of a VPC peering connection or a transit gateway together and Pinhole joins them, so chains are followed from one account or Region into another. Routes, network ACLs and security groups are checked on both sides, and so are security group references across the link where AWS supports them: same-Region peering, and transit gateways with referencing turned on.

Fixes and the fix plan

Pinhole only suggests changes it has proved.

For each exposure, it tries the narrowest changes first: replace the rule's source with exactly what uses it, cut the port out of a wider rule, allow it only from inside the VPC, remove the rule, add a network ACL deny, or remove the public IP. Each candidate is applied to a copy of the snapshot and the whole analysis runs again. A fix is verified only if the path is gone afterwards.

What a fix breaks

A change that closes an exposure can also cut traffic inside the network. For every fix, Pinhole measures every connection into and out of the interfaces it touches, before and after, with the same exact analysis, and reports what is lost. A lost connection counts as a break when there is evidence someone wants it: a load balancer reaching its targets, a health check on its own port, or a rule that names the source's security group. A connection allowed only by an address range is listed as a cut, since the snapshot cannot tell whether it is used. A verified fix that opens nothing and breaks nothing is marked safe.

The narrowest fix keeps that traffic on purpose: it finds the interfaces that reach the resource through the rule today, and replaces the rule's source with their security groups (or their addresses), so the internet loses access and they keep it. On an attack chain, the same rewrite keeps everyone except the attacker's foothold.

How the plan is chosen

  1. Candidates. The verified fixes for the worst open exposures, the rules on every route of the worst open attack chains, and the fixes at each chain's starting point, where one change can cut every chain from that server at once.
  2. Selection. Each round picks the change that removes the most weighted risk, with a penalty for closing paths that are probably wanted, and never a change that opens anything. Candidates that cannot win a round are not re-measured, which keeps it fast on large accounts.
  3. Pruning. When the plan is built, each step is taken out in turn and the rest re-applied. A step a later one made unnecessary is dropped. The tests check that every remaining step is needed.
  4. Proof. Every goal the plan closes needs some step that can touch its traffic, so the smallest set of candidates that touches them all is a lower bound (found exactly, by branch and bound). Every smaller set of candidates is then tried, smallest first. Since each candidate only takes access away, a set that leaves a goal open rules out all its subsets for free. If the search finishes, the plan is proved to be the fewest changes among those considered; if it runs out of budget, the bound is shown instead.

Breaks count against a step, so the plan prefers changes that keep wanted traffic. With a policy, connections its require rules need are never broken: a step that would break one is not taken.

The plan lists, for every step, what it closes, what chains it cuts, what else it affects, and the AWS CLI command. Anything no single change closes is listed for a person to decide.

Firewalls and appliances

Traffic that a route sends to an inspection endpoint is followed through it. AWS Network Firewall is evaluated rule by rule; third-party appliances are shown on the path and never quietly dropped from the report.

AWS Network Firewall

Pinhole reads each firewall, its policy and its rule groups, and follows the routes that send traffic to the firewall's endpoints: the internet gateway's own route table (ingress routing), the subnet routes that send replies back through the firewall, routes between subnets in a VPC, and a transit gateway sending traffic through an inspection VPC. On each path it evaluates the connection the way the firewall does:

  • Stateless rules per packet, in priority order, for the request and the reply: pass, drop or forward to the stateful engine; then the policy's default action.
  • Stateful rules per flow: 5-tuple rules, Suricata rules and domain lists, in default action order (pass, then drop, then reject, then alert) or strict order, with the strict default actions. HOME_NET and other variables are resolved from the rule group and the policy.
  • Per client port. Rules can treat client source ports differently, so the connection is decided for every client port range, the same way network ACL return traffic is.
  • Asymmetric routing. If only one direction of a connection passes a firewall, its stateful engine drops it, and the path says so.

A rule that also matches on content, a host name or an application protocol (for example pass http ... 8080) cannot be decided from configuration. Pinhole follows both outcomes; when they differ, the exposure is still reported, marked with a caveat that names the firewall and the reason. AWS managed rule groups are assumed to drop only known-malicious traffic.

Rule hygiene also covers the firewall: rules that never decide anything because rules the engine applies first, alone or together, already decide all of their traffic. A drop rule hidden behind a pass rule is the usual mistake, and is reported as medium.

Third-party appliances

A Gateway Load Balancer endpoint for a third-party appliance is followed like a firewall endpoint, but the appliance's rules are not visible to AWS APIs. Paths through it are assumed to pass, and every exposure through it says so, so it can be checked on the appliance itself.

Outbound traffic

The other direction: what each server can open to the internet. A database that can send any port to any address is an exfiltration path even when nothing can reach it.

For each interface the destination addresses and ports are cut at every rule that could decide differently, and one connection per cell is evaluated, exactly as for exposure:

  • the interface's security group must allow it out;
  • its subnet's route leads, possibly through firewalls, to the VPC's internet gateway, and the interface then needs a public IPv4 address or Elastic IP; or to a public NAT gateway that is available and whose own subnet routes to the internet gateway;
  • network ACLs allow the traffic out and the replies back at every subnet boundary, the NAT gateway's subnet included: replies reach the NAT gateway on its own ports (1024-65535) and the server on its ephemeral ports;
  • replies come back through the internet gateway, through the same firewalls.

Each finding names the gateway and the public address the traffic leaves as. Severity rises with the width of what is open and with whether the server holds data (a crown jewel tag, or a database port its security group lets in). Policies can say what must never, or must always, leave: {"deny": {"from": "prod-db", "to": "internet"}}.

On-premises networks

Site-to-Site VPN and Direct Connect are followed up to the AWS gateway, in both directions. Your own routers and firewalls are not visible to AWS, and every such path says so.

The links are virtual private gateways attached to a VPC, and VPN or Direct Connect gateway attachments of a transit gateway. The on-premises networks are what AWS routes to each link: VPC routes to a virtual private gateway (static, or propagated from BGP), transit gateway routes to a VPN or Direct Connect attachment, and the static routes of VPN connections. Tunnels that were down when the snapshot was taken are shown.

A connection from an on-premises address to a server works when:

  • the server's subnet routes the client's address back to a link, and the connection arrives over that same link (on-premises routing has to be symmetric with it);
  • over a virtual private gateway, its route table (ingress routing), if it has one, sends the traffic to the subnet, possibly through a firewall; over a transit gateway, the attachment's route table sends it to the VPC, and the attachment subnet's network ACL and routes apply;
  • the network ACLs and the security group allow the client's own address (security groups cannot reference on-premises groups), and replies back on its ephemeral ports.

Outbound to an on-premises address is decided the same way, ending at the link. pinhole can and the console's query page take on-premises addresses on either side, and policies take "from": "onprem".

PrivateLink

An endpoint service puts a load balancer inside other accounts' networks. Who may connect is a list of principals, and "*" means every AWS account.

For each endpoint service you provide, Pinhole reads the allowed principals, whether connections need your approval, and the endpoints connected from other accounts and Regions. Behind it, for each Network Load Balancer listener, it works out which consumer addresses get in: the load balancer's security groups apply to PrivateLink traffic unless that is switched off, and then, as with no security groups at all, any address gets in. Targets see the load balancer's own address, never the consumer's, so each target is checked from the load balancer with the full path model.

On your side, it lists your interface and gateway endpoints: who in the network can use them, whether the service belongs to another account, and whether the endpoint policy still allows everything. On an S3 or DynamoDB endpoint, a policy like that lets data be copied to buckets and tables in any account; limiting it to your organization's resources closes that.

Privacy and security

  • Read-only collection. Only Describe, Get and Search calls, enforced in code and tested against the IAM policy.
  • Nothing is uploaded. The console has no server. Its Content Security Policy blocks every network request, and only its own script, identified by hash, may run.
  • Nothing is changed. Fixes are printed as commands for you to review and run.
  • Input is validated. Snapshots, change lists and Terraform plans are checked field by field before use, and text from them is escaped everywhere it is shown.
  • No secrets in the repository, and real snapshots are kept out of it by .gitignore.

To report a vulnerability, use GitHub's private reporting on the repository, as described in SECURITY.md.

Accuracy

Every rule Pinhole models comes from AWS documentation, and the documentation is cited in the code, the tests and the findings.

Each evaluation rule has unit tests. On top of those, hand-written scenarios with known answers cover the cases that are easy to get wrong:

ScenarioWhat it proves
01Network ACL return traffic on ephemeral ports: full, partial, none
02Security group references match group members only, never internet clients
03Longest-prefix routing combined with peering, which is not transitive
04Blackhole routes in VPC and transit gateway route tables
05Peering where the far side has no route back
06A public IP without an internet gateway route
07An internet-facing ALB in front of private instances
08NLB without security groups, client IP preservation on and off
09Attack chains, the best fix, and what a change closes and leaves open
10IPv6 without a public IP, egress-only gateways, IPv6 ACL rules
11Attack chains across two peered accounts
12AWS Network Firewall at the internet edge, rules decided per client port
13Centralised inspection through a transit gateway and an inspection VPC
14What servers can send out, through an internet gateway or a NAT gateway
15Site-to-Site VPN and Direct Connect, through a virtual private gateway and a transit gateway
16PrivateLink services open to every account or a partner, and endpoint policies that allow everything

Checked against a second implementation

A separate reference evaluator, written from the AWS documentation one packet at a time and sharing no code with the engine, answers the same questions on random networks: random routes (including blackholes and NAT), network ACLs, security groups, public addresses and gateways. Every test run checks the engine against it on 400 networks and over 120,000 questions, both through the packet evaluator and the exposure report, and any disagreement fails the build with the network that caused it. Rule compaction is checked the same way, and so is Network Firewall: random stateless and stateful policies, in both rule orders and with every default action, are decided per client port by the engine and by a separate reference, and have agreed on 4,000 policies (360,000 connections). The test takes a larger count with PINHOLE_FUZZ_RUNS; it has been run on 6,000 networks (1.8 million questions) without a difference.

Continuous integration runs every test on Node 22 and 24, and runs both collectors against a fake AWS built from the scenarios. The full model, with every simplification, is in docs/model.md. If you find a wrong result, report it; it becomes a new scenario.

Limitations

Read these before relying on a clean report. Anything detected but not analysed is listed on the Coverage page.

  • Scope. VPC network paths to interfaces and Application and Network Load Balancers. Not S3, API Gateway, Lambda function URLs, CloudFront, or other services that are public outside a VPC. Use a configuration scanner such as Prowler or AWS Security Hub for those.
  • Followed, with a caveat. Third-party appliances behind Gateway Load Balancer endpoints (their rules are not visible), Network Firewall rules that match on content or host names, and the on-premises side of VPN and Direct Connect.
  • Detected, not modelled. Routes to instances or interfaces acting as appliances, Global Accelerator and Classic Load Balancers. Paths through them are reported as unknown.
  • IPv6 is analysed for TCP and UDP to interfaces and dual-stack load balancers. Not yet for ICMPv6 or IPv6 lateral movement.
  • Wanted traffic is inferred. Fixes count a lost connection as a break only with evidence it is wanted: a load balancer and its targets, a health check, or a rule that names the source's group. Traffic allowed only by an address range may or may not be used; flow logs are not read. A policy's require rules make any connection count.
  • Configuration, not traffic. Host firewalls, the operating system and whether anything listens on the port are outside the model. Existing connections can outlive a rule change.
  • Snapshots are a point in time. Collect again after changes, or compare two snapshots.
  • Size. The console handles files up to 200 MB. Very large accounts are faster with the CLI.

Questions

Does Pinhole need access to my AWS account?

Only to collect a snapshot, with read-only calls. The analysis never touches AWS. You can collect in CloudShell and never give Pinhole credentials at all.

Is my data sent anywhere?

No. The console has no server and is not allowed to make network requests. The CLI makes no requests except the AWS calls of pinhole collect.

How is this different from looking at security groups?

A security group is one of six things that decide reachability. Pinhole combines all of them, including network ACLs in both directions, routes, load balancers and peering, and tells you which one decided the answer.

Will applying the fix plan break my application?

Every step lists the other paths it closes. Closing medium- or low-risk paths, such as web traffic, counts against a change when the plan is chosen, and any step that still does so is shown with a warning. Review each command before running it.

How many accounts can I analyse?

As many snapshots as you load. Each covers one account in one Region. Linked accounts are joined automatically to follow attack chains between them.

What does it cost?

Nothing. Pinhole is MIT-licensed. The read-only describe calls it makes are free, and CloudShell is free to use.
