See what the internet can reach in your AWS network.

Pinhole reads how your VPCs are configured, works out every path from the internet to your servers and load balancers, follows what an attacker could reach next, and gives you the fewest rule changes that close it. Every answer is exact, explained hop by hop, and checked by running the analysis again.

Free and open source (MIT). Runs in your browser or on the command line. Nothing is uploaded, and nothing in AWS is changed.

Three questions, answered exactly

What can the internet reach?

Every network interface and load balancer listener that accepts connections from the internet, with the exact ports, the exact source addresses that work, and the rule behind each hop.

What can an attacker reach next?

If one of those servers is compromised, the databases, caches, control planes and admin ports it can open, inside your VPCs and across peered accounts.

What is the smallest fix?

The fewest changes that close every critical and high risk. Each one is applied to a copy of your network and re-analysed, so it is proved, with the AWS CLI command to run.

Why it exists

Whether a server is reachable from the internet depends on five things at once: a public address, an internet gateway, the subnet's routes, the network ACL in both directions, and every security group on the interface. A load balancer adds its own groups, ACLs and targets. The AWS console shows each of these on its own page; none of them answers "is this open, and why?"

Getting it wrong goes both ways. A rule that looks open can be harmless because the response has no route back. A rule that looks narrow can be wide open because another group on the same interface allows everything. Pinhole puts all of it together and gives one answer, with the evidence.

Who it is for

  • Cloud and platform engineers who want to know what a change really opens before and after they make it.
  • Security teams who need a complete, defensible list of internet exposure and attack paths, not a sample.
  • Auditors and managers who need a clear report they can read without opening the AWS console.

What it is not

Pinhole analyses configuration, not traffic. It does not scan your servers, read logs, or know what software listens on a port. It covers VPC network paths to interfaces and Application and Network Load Balancers; services that are public by design outside a VPC, such as S3 buckets or API Gateway, are out of scope. See Limitations.

How it works

Three steps. Only the first one touches AWS, and it only reads.

  1. Collect

    A short script in AWS CloudShell, or pinhole collect, calls read-only Describe APIs and saves one JSON file per account and Region: the snapshot.

  2. Analyse

    Open the snapshot in the console or the CLI. The analysis runs on your machine, offline. It cuts the address and port space at every rule boundary, so every client and every port is covered, not sampled.

  3. Act

    Read the exposures, attack chains and the fix plan. Try changes in the simulator. Copy the AWS CLI commands you agree with and run them yourself.

Exact, not sampled

For each interface, Pinhole collects every boundary that any relevant rule draws: CIDR edges, port range edges, ACL rule edges. Between two boundaries every packet is treated the same way by every rule, so evaluating one packet per piece gives the answer for all of them. That is how a report can say "tcp/22 from 0.0.0.0/0 except 10.0.0.0/8" and be right about every address.

Reachable, blocked or unknown

Reachable
Every step allows the request and the response.
Blocked
A named step stops it, with the rule or the missing route.
Unknown
The snapshot lacks what the answer depends on, for example a route table in another account or a firewall appliance in the path. Pinhole never guesses.

Quick start

Five minutes in the browser, with nothing to install. The command line is below.

In the browser

  1. Open the console. It starts on a demo environment, clearly labelled, so you can look around first.
  2. Choose Connect an account. It shows one command to paste into AWS CloudShell, which writes pinhole-snapshot-<account>-<region>.json.
  3. Download the file from CloudShell (Actions, then Download file) and drop it on the console.

The console is one HTML file. It makes no network requests, and its Content Security Policy makes the browser enforce that, so your snapshot never leaves the tab. You can also download pinhole-<version>.html from a release and open it from disk.

On the command line

Requires Node.js 22 or later.

git clone https://github.com/w3bcooki3/pinhole.git
cd pinhole
npm ci && npm run build
alias pinhole="node $PWD/packages/cli/dist/main.js"

pinhole collect --profile audit --region eu-west-1
pinhole exposure pinhole-snapshot-*.json

Collect a snapshot

A snapshot is a JSON file with the network configuration of one account in one Region. Collection uses read-only calls and takes seconds.

In AWS CloudShell

No install and no credentials on your machine. Open CloudShell in the account to check, upload cloudshell-collect.sh (the console's Connect page gives a copy-ready command that writes it for you) and run:

bash cloudshell-collect.sh eu-west-1

# several Regions
for r in us-east-1 eu-west-1 ap-southeast-2; do bash cloudshell-collect.sh "$r"; done

Download each file with Actions, then Download file, using the path the script prints.

From your machine

pinhole collect --profile audit --region eu-west-1
# writes pinhole-snapshot-<account>-eu-west-1.json, readable only by you

pinhole collect --profile audit --region us-east-1,eu-west-1 --out-dir snapshots
# one file per Region; a Region that fails does not stop the others

Permissions

The collector needs only the read-only actions in this policy. A test checks that the policy and the collector's API calls match exactly, and the collector refuses at runtime to send any call whose name does not start with Describe, Get or Search. If a call is denied, collection continues and the report says which results may be incomplete.

What a snapshot contains

VPCs, subnets, route tables, internet, NAT and egress-only gateways, peering connections, transit gateways and their route tables, network ACLs, security groups and rules, prefix lists, network interfaces, instance names, VPC endpoints, and load balancers with their listeners, rules, target groups and target health. No data from inside your servers, no credentials, no logs. It does contain your account ID, private and public IP addresses and resource names, so treat it as internal.

In CI and pull requests

Catch new internet exposure before it ships: check a Terraform plan, compare snapshots, or publish findings to GitHub code scanning.

Check a Terraform plan

Pinhole places each security group, rule, network ACL, route, attachment, Elastic IP, subnet association, internet gateway and listener change from the plan onto the snapshot, IPv4 and IPv6, including groups and gateways the plan creates, and runs the full analysis. Anything it cannot place exactly is listed as not analysed, never guessed.

terraform plan -out tfplan && terraform show -json tfplan > plan.json
pinhole plan snapshot.json plan.json --fail-on high

GitHub Action

The action reads files in the workspace and never calls AWS. It writes the result to the job summary and fails the job at the level you choose.

- uses: actions/checkout@v4

- uses: w3bcooki3/pinhole@v0.2.0
  with:

    plan: plan.json
    fail-on: high

Internet exposure

An interface is exposed on a port when a client on the internet can open a connection to it and get the answer back.

Over IPv4, that needs all of these:

  1. A public IP or Elastic IP on the interface.
  2. An internet gateway attached to the VPC.
  3. The network ACL allowing the request in.
  4. A security group on the interface allowing it.
  5. The subnet's route for the client's address pointing at that internet gateway.
  6. The network ACL allowing the response out, on the client's ephemeral port.

Over IPv6 no public IP is needed: any interface with an IPv6 address in a subnet routed to an internet gateway is checked, and so is every listener of a dual-stack load balancer. Load balancers are checked from the internet to the listener, then from each load balancer node to each target.

Return traffic

Security groups are stateful: if the request is allowed, so is the response. Network ACLs are not. The response leaves on the client's ephemeral port, and that range depends on the client: Linux uses 32768 to 61000, Windows 49152 to 65535, and Elastic Load Balancing 1024 to 65535. An ACL that only allows one of these ranges out works for some clients and not others. Pinhole reports that as partial, per client.

Severity

Exposures are ranked by what is on the port, whoever it is open to. Remote administration (SSH, RDP, WinRM and similar), databases and caches, and container and cluster control planes are critical. Admin panels, file sharing, directory services and message brokers are high, and so is any range of many ports. A port Pinhole does not recognise is medium. Plain web traffic on 80 and 443 is low, because it is usually meant to be public. The list is in packages/engine/src/risk.ts; it does not know what actually runs on a port.

Attack chains

If an internet-facing server is compromised, what can the attacker open from there?

Each server the internet can reach is treated as a starting point. From it, Pinhole works out every service it can open on every other interface, with the same exact analysis. The attacker moves on only through services that normally give command execution: remote administration, container and cluster control planes, and wide port ranges. A database reached on 5432 is a target, not a new foothold.

A chain is reported when it ends at a data store, a control plane or remote administration that the internet cannot reach directly. Chains to the same target are merged, with every route listed. Severity comes from what is reached, lowered when the starting point is only open on web ports, or when the chain is three hops or longer.

This is a model of what the network allows, not of what is exploitable: it assumes credentials or a vulnerability at each step.

Across accounts and Regions

Load snapshots from both sides of a VPC peering connection or a transit gateway together and Pinhole joins them, so chains are followed from one account or Region into another. Routes, network ACLs and security groups are checked on both sides, and so are security group references across the link where AWS supports them: same-Region peering, and transit gateways with referencing turned on.

Fixes and the fix plan

Pinhole only suggests changes it has proved.

For each exposure, it tries the narrowest changes first: cut the port out of a wider rule, allow it only from inside the VPC, remove the rule, add a network ACL deny, or remove the public IP. Each candidate is applied to a copy of the snapshot and the whole analysis runs again. A fix is verified only if the path is gone afterwards. Every other path the change closes is shown, so you can see if it breaks something you want.

How the plan is chosen

  1. Candidates. The verified fixes for the worst open exposures, the rules on every route of the worst open attack chains, and the fixes at each chain's starting point, where one change can cut every chain from that server at once.
  2. Selection. Each round picks the change that removes the most weighted risk, with a penalty for closing paths that are probably wanted, and never a change that opens anything. Candidates that cannot win a round are not re-measured, which keeps it fast on large accounts.
  3. Pruning. When the plan is built, each step is taken out in turn and the rest re-applied. A step a later one made unnecessary is dropped. The tests check that every remaining step is needed.

The plan lists, for every step, what it closes, what chains it cuts, what else it affects, and the AWS CLI command. Anything no single change closes is listed for a person to decide.

Privacy and security

  • Read-only collection. Only Describe, Get and Search calls, enforced in code and tested against the IAM policy.
  • Nothing is uploaded. The console has no server. Its Content Security Policy blocks every network request, and only its own script, identified by hash, may run.
  • Nothing is changed. Fixes are printed as commands for you to review and run.
  • Input is validated. Snapshots, change lists and Terraform plans are checked field by field before use, and text from them is escaped everywhere it is shown.
  • No secrets in the repository, and real snapshots are kept out of it by .gitignore.

To report a vulnerability, use GitHub's private reporting on the repository, as described in SECURITY.md.

Accuracy

Every rule Pinhole models comes from AWS documentation, and the documentation is cited in the code, the tests and the findings.

Each evaluation rule has unit tests. On top of those, hand-written scenarios with known answers cover the cases that are easy to get wrong:

ScenarioWhat it proves
01Network ACL return traffic on ephemeral ports: full, partial, none
02Security group references match group members only, never internet clients
03Longest-prefix routing combined with peering, which is not transitive
04Blackhole routes in VPC and transit gateway route tables
05Peering where the far side has no route back
06A public IP without an internet gateway route
07An internet-facing ALB in front of private instances
08NLB without security groups, client IP preservation on and off
09Attack chains, the best fix, and what a change closes and leaves open
10IPv6 without a public IP, egress-only gateways, IPv6 ACL rules
11Attack chains across two peered accounts

Continuous integration runs every test on Node 22 and 24, and runs both collectors against a fake AWS built from the scenarios. The full model, with every simplification, is in docs/model.md. If you find a wrong result, report it; it becomes a new scenario.

Limitations

Read these before relying on a clean report. Anything detected but not analysed is listed on the Coverage page.

  • Scope. VPC network paths to interfaces and Application and Network Load Balancers. Not S3, API Gateway, Lambda function URLs, CloudFront, or other services that are public outside a VPC. Use a configuration scanner such as Prowler or AWS Security Hub for those.
  • Detected, not modelled. AWS Network Firewall, Gateway Load Balancer, routes to appliances, gateway route tables, Global Accelerator, Classic Load Balancers, VPN and Direct Connect. Paths through them are reported as unknown.
  • IPv6 is analysed for TCP and UDP to interfaces and dual-stack load balancers. Not yet for ICMPv6 or IPv6 lateral movement.
  • Configuration, not traffic. Host firewalls, the operating system and whether anything listens on the port are outside the model. Existing connections can outlive a rule change.
  • Snapshots are a point in time. Collect again after changes, or compare two snapshots.
  • Size. The console handles files up to 200 MB. Very large accounts are faster with the CLI.

Questions

Does Pinhole need access to my AWS account?

Only to collect a snapshot, with read-only calls. The analysis never touches AWS. You can collect in CloudShell and never give Pinhole credentials at all.

Is my data sent anywhere?

No. The console has no server and is not allowed to make network requests. The CLI makes no requests except the AWS calls of pinhole collect.

How is this different from looking at security groups?

A security group is one of six things that decide reachability. Pinhole combines all of them, including network ACLs in both directions, routes, load balancers and peering, and tells you which one decided the answer.

Will applying the fix plan break my application?

Every step lists the other paths it closes. Closing medium- or low-risk paths, such as web traffic, counts against a change when the plan is chosen, and any step that still does so is shown with a warning. Review each command before running it.

How many accounts can I analyse?

As many snapshots as you load. Each covers one account in one Region. Linked accounts are joined automatically to follow attack chains between them.

What does it cost?

Nothing. Pinhole is MIT-licensed. The read-only describe calls it makes are free, and CloudShell is free to use.
